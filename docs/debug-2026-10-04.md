## Fixed defects

| Trigger | Previous behavior | Corrected behavior |
| --- | --- | --- |
| Unauthenticated webhook submits an update ID | `botapi.php` consumed the ID before authentication, suppressing the legitimate update for 120 seconds | Only the authenticated webhook consumes IDs; API/payment/job includes do not consume them |
| Digital purchase target contains `&`, quotes, or HTML-sensitive characters | HTML escaping changed the quoted target and changed it again during purchase, breaking the order-state comparison | Quote/purchase preserves the original target and retains provider validation and output escaping |
| Customer submits the ID of a panel hidden from them | Mini App/mobile catalogs omitted the panel, but direct sales requests could still reach checkout | Sales checks apply `hide_user` consistently, including numeric and string user IDs |
| Payment diagnostic query fails while `SELECT 1` succeeds | Unknown counts became zero in health snapshots/history and could appear healthy | Unknown counts remain `-1`, render as unknown, and flag review in the panel/dashboard |
| Active bot is renamed on Telegram | Each webhook extended the username cache's six-hour freshness, indefinitely postponing `getMe` | Freshness tracks successful `getMe` separately from host/cache writes; failed checks retry after one minute |
| AqayePardakht callback submits another invoice's transaction ID | The transaction was verified without a stored binding to the selected invoice | Checkout stores `transid`; callback requires an exact match before verification or payment claim |

Three existing source-contract tests also interpolated undefined PHP variables

## Compatibility

Existing AqayePardakht invoices without a stored transaction ID cannot be safely
bound retrospectively. Their callbacks return HTTP 409 with guidance to create a
fresh invoice, or contact support if already paid. Such payments require manual
review; the callback does not automatically credit or deliver them.

## Further audit leads

The following observations need separate reproduction and scoped fixes; they
are not covered by this patch:

- `BluebotDigitalServices::deliver()` dispatches using the current product's
  provider/type, while an order retains its original provider. Editing a product
  between checkout and approval could change fulfillment routing.
- Provider reconcilers select bounded batches by ascending order ID. An old batch
  that remains processing or repeatedly fails can delay newer orders indefinitely.
- Some cashback callbacks, including AqayePardakht, add rewards by overwriting a
  previously read wallet balance. Concurrent balance changes could be lost;
  these paths should use the atomic wallet operation.
